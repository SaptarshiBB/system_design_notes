§01

Introduction to System Design

System Design is the process of defining the architecture, components, interfaces, and data flow of a system so it satisfies real requirements — the blueprint of a software building, drawn before any code exists.

Analogy: designing a city. You decide where roads go, where hospitals sit, how electricity flows — before any construction. System Design does the same job for software.

Why it matters

Interviews

FAANG and top companies treat it as a core round, separate from coding rounds.

DevOps

Understanding system flow is what lets you deploy, monitor, and scale confidently.

Real world

Poor design shows up as crashes, data loss, and users who leave.

Career growth

Senior engineers are judged less on syntax, more on systems thinking.

§03

DNS — Domain Name System

DNS turns human-readable names like google.com into IP addresses like 142.250.80.46. Without it, you'd have to memorize an IP for every site you visit.

DNS is your phone's contact list — you search "Mom" and it finds the number. You never memorize the number itself.

Load Balancing

A load balancer sits in front of your servers and spreads incoming traffic across them — a traffic officer directing cars so no single lane jams up.

Health checks: the LB pings every server on an interval. A server that stops responding is pulled out of rotation until it recovers.

Rate Limiting

Rate limiting caps how many requests a user or IP can make in a time window — protection against abuse, DDoS, and accidental overuse. Exceed it, and you get HTTP 429.

§07

Caching

Cache frequently-read data in fast memory so future requests skip the slow database entirely.

Instead of walking to the library every time, you keep the most-used books on your desk. The desk is the cache; the library is the database.
LIVE SIMULATOR — CACHE HIT vs MISS
Try requesting user_id=123 a few times.
StrategyHowProsCons
Write-ThroughWrite to cache + DB togetherAlways consistentSlower writes
Write-BackWrite cache first, sync laterFast writesRisk of loss on crash
Write-AroundWrite straight to DBCache stays cleanFirst read is slow

Eviction policies

LRU

Evict the item unused for the longest time.

LFU

Evict the item accessed the fewest times.

FIFO

Evict the oldest item, regardless of use.

TTL

Every item expires after a fixed duration.

Cache stampede: when a hot key expires, thousands of requests can hit the DB at once. Fix with a mutex lock or probabilistic early expiration.
§08

CDN — Content Delivery Network

A globally distributed set of edge servers that cache and serve static content close to the user, so nobody has to reach across an ocean for a JPEG.

ORIGIN + EDGE NETWORK
FeatureWithout CDNWith CDN
Latency (India user, US origin)~200ms~5-20ms
Origin load100% of requests~5% (cache misses only)
AvailabilityDown if origin failsEdge serves cached content
Popular CDNs: CloudFront (400+ edge locations), Cloudflare (300+ cities), Fastly, Akamai. Interview shorthand: CDN = static content + low latency + offload origin.

Database Scaling

Reads usually outnumber writes by a wide margin — so replicate for reads, and shard when a single machine can't hold the data anymore.

READ REPLICAS
SHARDING — 100M ROWS SPLIT ACROSS 4 SHARDS
Sharding gives unlimited horizontal scaling but cross-shard queries, joins, and rebalancing all get painful.

Microservices Architecture

Breaking one big application into small, independently deployable services — each with its own database.

MONOLITH vs MICROSERVICES
AspectMonolithMicroservices
DeploymentWhole app each timeIndividual services
ScalingScale entire appScale only what's needed
Failure impactOne bug, whole app downIsolated to one service
Best forSmall teams, MVPsLarge teams, complex domains
API Gateway pattern: clients never call microservices directly. All requests pass through one gateway handling auth, rate limiting, routing, and SSL termination.

High Throughput Systems

Find where the request slows down, then fix that specific hop.

FINDING THE BOTTLENECK
ProblemFixImpact
Slow DB queriesAdd indexes, optimize query10-100x speedup
Repeated computationCache results (Redis)~99% reduction
Slow external APIsAsync + timeout + fallbackNo blocking
High write loadWrite-behind cache + batching10x throughput
Metrics that matter: p99 latency (not average!), throughput (RPS), error rate (<0.1% target), and availability (99.99% = 52 min/yr downtime).

ConceptMeaningExample

System Design Cheat Sheet

Quick decision framework — what to reach for, and when.

Need low-latency reads?

Add a cache (Redis).

Serving static files fast?

Use a CDN.

Lots of users to scale?

Horizontal scale + load balancer.

Write-heavy workload?

Write-back cache + async queue.

Read-heavy DB?

Read replicas.

Huge DB table?

Shard by a natural key.

Services calling each other?

Decouple with a message queue.

Need real-time?

WebSockets (chat, live feeds).

Need bank-grade consistency?

SQL + strong consistency (CP).

Need social-scale speed?

NoSQL + eventual consistency (AP).

Need auto-deploy?

Docker + Kubernetes.

Unpredictable spikes?

Serverless (Lambda) or auto scaling.
